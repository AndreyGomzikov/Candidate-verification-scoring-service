# Доработка `/status`: краткая история всех заявок

Основа: приложенный архив `Candidate-verification-scoring-service(20261109-105114).rar` (содержимое совпадает по SHA-256 с архивом 08:21:49). Изменено только отображение статуса и способ отправки отчёта. Алгоритмы проверки, Telegram approve/decline, пороги скоринга, таблицы PostgreSQL и анкета не изменялись.

## Поведение

- Единственная команда отчёта — `/status`. `/status full` не поддерживается.
- Команду отправляют **в личном чате с @Solidus_gatekeeper_bot**. После проверки прав бот отвечает краткой статистикой и списком **всех зарегистрированных** заявок за всё время работы БД. Если вся история превышает лимит Telegram, он отправляет **одно сообщение с TXT-файлом** `solidus-status-all.txt`, содержащим полную статистику и все заявки. Никаких отдельных сообщений `История 1/N` нет.
- Каждая запись истории: номер заявки, время UTC, имя, username, TG ID, фактический исход, три ответа (каждый до 100 символов, отдельной пронумерованной строкой с названием вопроса), Confidence Score (при наличии), причина (до 120 символов). Оценка `0/100` показывается **только при реально записанном нулевом балле**.
- Для таймаута выводится точно **«Анкета не завершена. Баллы: не рассчитывались»**. При `expired` из-за `Hide_requester_missing` выводится отдельный исход «ЗАЯВКА ОТСУТСТВУЕТ В TELEGRAM», чтобы не смешивать техническое отсутствие заявки с таймаутом.
- Повторные попытки во время cooldown показываются отдельно с их собственным результатом. Отсутствующие в PostgreSQL события Telegram, включая случай с Габриэллой, задним числом не восстанавливаются.
- Никаких автоматических отчётов/уведомлений не добавлено. Доступ к истории только по запросу.

## Доступ

Если `ADMIN_USER_IDS` в `.env` **задан**, Telegram ID Евгения (214627463) или других нужных администраторов должен быть в этом списке. Если переменная не задана или пуста, проверяются текущие права владельца/администратора **основной группы** через Telegram API. Администраторы только канала модерации не получают доступ. Обычные пользователи не получают отчёты. В канал модерации ответы кандидатов не публикуются.

## Какие файлы изменены

- `app/status_report.py`: короткий формат, точные статусы и безопасный учёт Telegram UTF-16 лимита.
- `app/handlers.py`: единственный вариант `/status`, доступ по правам, единый текстовый отчёт или один TXT-документ, если история длинная, защита от параллельного запуска одной и той же отправки.
- `app/main.py`: `block=False` у CommandHandler(`status`), чтобы отправка большой истории не задерживала обработку новых `chat_join_request`.
- `tests/test_status_history.py`: тесты статусов, прав, лимита Telegram, неполных анкет, cooldown, больших историй и одновременных запросов.
- `README.md`: описание функции.

Новые миграции и переменные окружения не требуются. Таблицы не менялись.

## Безопасный перенос изменений

1. Сделайте резервную копию рабочего кода и базы данных по вашему стандартному процессу. Не распаковывайте ZIP с принудительной перезаписью поверх репозитория, не сравнив изменения с последней серверной версией.
2. В рабочей ветке сравните три runtime-файла из `solidus_status_only_patch.zip` с `app/` репозитория. Перенесите изменения с учётом всех более поздних правок.
3. Выполните тесты в среде разработки: `python -m pytest -q`.
4. Убедитесь, что Евгений авторизован (см. `ADMIN_USER_IDS`); **не присылайте `.env`, токен бота или ключи в чат**.
5. После проверки в тестовой среде разверните штатно:

```bash
cd /var/sftp/AI-Gatekeeper/current
docker compose up -d --build gatekeeper
docker compose ps
docker compose logs --since=3m gatekeeper
```

6. В личном чате администратора проверьте `/status`: статистику, дату последней заявки, фактические ответы, баллы, незавершённую анкету №38 и отсутствие заявки №31 в группе таймаутов.

**Ограничение:** отчёт отражает записи в PostgreSQL, но не является Telegram-списком всех ожидающих заявок. Текущая версия не обеспечивает восстановление пропущенных событий `chat_join_request`.
