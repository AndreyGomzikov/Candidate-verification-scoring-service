# Solidus AI Gatekeeper — учёт входящих заявок и устойчивость доставки

Основа: архив `Candidate-verification-scoring-service(20261109-114926).rar` от 09.11.2026.

## Что изменено

1. Каждое **полученное ботом** `chat_join_request` сразу регистрируется в новой таблице `join_request_events` с `update_id`, Telegram ID пользователя, группой и датой запроса. `update_id` уникален — повторная доставка того же обновления не создаёт новую запись учёта.
2. Создание анкеты и приём Telegram API первой отправки фиксируются раздельно. В случае успешного `send_message` сохраняется `first_message_id`. Это **подтверждение принятия сообщения Telegram API**, а не факт прочтения кандидатом.
3. При TelegramError в первом сообщении анкета переходит в `pending_admin`, а не в автоматический отказ. В журнал пишется тип ошибки. Бот пытается отправить карточку модератору, а при неудаче оставляет устойчивый маркер для повторной отправки.
4. Если бот завершил работу после создания записи, но до подтверждения первого сообщения, фоновая проверка после 90 секунд обозначает отправку как неподтверждённую, направляет активную анкету на ручную проверку и сообщает модераторам. **Автоматически повторно отправлять первый вопрос не пытается:** при сетевом таймауте он мог быть доставлен.
5. Если событие получено и сохранено, но анкета так и не создана, в `/status` появится отдельная техническая запись вида `Событие Telegram U... — АНКЕТА НЕ СОЗДАНА`. События с кандидатами показываются через обычную строку кандидата, без дублей.
6. Появился общий обработчик исключений приложения, чтобы непредвиденные ошибки не выводились как `No error handlers are registered`.
7. `/status` сохраняет краткий отчёт за весь период, с тремя ответами по отдельным строкам и фразой `Анкета не завершена. Баллы: не рассчитывались`. Для технических случаев `pending_admin` указывается `ТЕХНИЧЕСКАЯ ПРОБЛЕМА — РЕШЕНИЕ АДМИНИСТРАТОРА`.

## Ограничения

- Бот **не может** получить старые ожидающие заявки из Telegram задним числом по Bot API. Заявка Габриэллы от 5 ноября не появится автоматически, если Telegram не доставлял её боту и нет записи в БД.
- Запись `first_question_sent` означает только, что Telegram **принял API-запрос**; факт прочтения пользователем неизвестен.
- Предупреждения модератору отправляются с гарантией **«не менее одного раза»**: при аварийном перезапуске между успешным `send_message` и отметкой о доставке карточка может прийти повторно. Дубли не выполняют действий принятия/отклонения.
- Сохранённые ранее записи кандидатов не имеют исторического `join_request_events`; подделывать такие события в БД нельзя.
- В окружении проверки доступна SQLAlchemy, но нет `aiosqlite`, `asyncpg` и настоящего Telegram API: реальные интеграционные проверки базы и Telegram **ещё необходимо провести на тестовом сервере**. Код новых таблиц проверен компиляцией под PostgreSQL/SQLite и синхронным тестом SQLite; остальные unit-тесты пройдены.

## Безопасное внедрение

Прежде чем менять рабочий сервер, проверьте diff с текущей веткой (на сервере могли появиться другие изменения). Пакет `solidus_gatekeeper_reliability_patch.zip` содержит только перечисленные изменения; полный ZIP — снимок проекта без `.git` и секретов.

**1. Резервная копия PostgreSQL:**

```bash
cd /var/sftp/AI-Gatekeeper/current
mkdir -p ../backups
docker compose exec -T postgres pg_dump -U gatekeeper -d gatekeeper -Fc \
  > ../backups/gatekeeper_before_join_audit_$(date +%Y%m%d_%H%M%S).dump
```

**2. Проверка и установка:** Перенести изменённые файлы в рабочую ветку, выполнить локальную проверку и выкатить через обычный Git/CI. Не распаковывать ZIP поверх работающего проекта без diff. После проверки на тестовом стенде:

```bash
cd /var/sftp/AI-Gatekeeper/current
docker compose up -d --build gatekeeper
docker compose ps
docker compose logs --tail=120 gatekeeper
```

Новая таблица создаётся при старте `db.init()` через `Base.metadata.create_all`, существующие заявки не удаляются.

**3. Проверка таблицы только чтением:**

```bash
docker compose exec -T postgres psql -U gatekeeper -d gatekeeper -c \
  "SELECT to_regclass('public.join_request_events');"

docker compose exec -T postgres psql -U gatekeeper -d gatekeeper -c \
  "SELECT update_id, user_id, candidate_id, status, first_message_id, error_type, alert_required, admin_alerted_at FROM join_request_events ORDER BY id DESC LIMIT 15;"
```

**4. Приёмочный тест Telegram:** После готовности тестовой группы, с отдельного тестового аккаунта подать *новую* заявку. Проверить, что логи содержат `join_request_received`, `join_candidate_created`, `join_first_question_sent`, а `first_message_id` записан в БД. Проверить `/status` в личном чате администратора. Никаких действий с заявками действующих кандидатов для теста не требуется.

**5. Проверка аварийного сценария на тестовой БД:** Убедиться, что заявка с неподтверждённой отправкой переходит в `pending_admin`, что карточка приходит в канал модерации и что повторная попытка отправки карточки при временном сбое восстанавливается. Не имитировать ошибки на продуктивном Telegram.

**6. Удаление/откат:** Откатить только код через предыдущий commit/образ. Новая таблица безопасно остаётся в БД; её удалять при откате не требуется. Повторное развёртывание обновлённого кода использует те же записи учёта.

## Диагностика после установки

```bash
cd /var/sftp/AI-Gatekeeper/current

docker compose logs --since=2h gatekeeper 2>&1 | \
  grep -Ei 'join_request_received|join_candidate_created|join_first_question_sent|Join request processing interrupted|Failed to start interview|join_admin_alert_sent|Failed to alert admin'
```

Для случая без ответа кандидата сначала сопоставить `first_message_id` в `join_request_events`. Если он есть, Telegram принял сообщение, но это не означает, что пользователь его прочитал. Если `status=delivery_unconfirmed` или `first_question_failed`, необходимо ручное рассмотрение.
