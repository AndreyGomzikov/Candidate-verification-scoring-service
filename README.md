# Микросервис «Верификация и скоринг кандидатов»

Telegram-микросервис для автоматической верификации и скоринга кандидатов перед вступлением
в закрытый чат Solidus.

## Что реализовано по ТЗ

1. Перехват `ChatJoinRequest` целевого Telegram-чата.
2. Немедленный старт диалога с кандидатом в ЛС.
3. Последовательная анкета из трех обязательных блоков:
   - локация / Батуми / Аджария / даты приезда;
   - бизнес-профиль, роль, ниша, ссылки;
   - цель вступления и потенциальная польза сообществу.
4. AI-скоринг:
   - `location_score`;
   - `business_score`;
   - `intent_score`;
   - `spam_score`;
   - `ai_confidence`;
   - итоговый `Confidence Score`;
   - краткое русскоязычное саммари и флаги риска.
5. Автоотказ только при очевидном спаме или очевидном несоответствии одному из ключевых критериев
   и только при высокой уверенности AI.
6. Все остальные кандидаты уходят в закрытый админ-чат карточкой с кнопками
   `Одобрить` / `Отклонить`.
7. Решение администратора вызывает Telegram API `approveChatJoinRequest` / `declineChatJoinRequest`.
8. Состояние анкеты и результаты скоринга сохраняются в БД.
9. При сбое AI кандидат не отклоняется автоматически: заявка уходит администратору с пометкой об ошибке.
10. При ошибке Telegram API статус в БД меняется только после подтверждённого `approve/decline`; технический сбой не превращается в ложный отказ.
11. Для последующих уведомлений сохраняется реальный private chat ID из диалога с кандидатом; код не предполагает, что `user_id == chat_id`.
12. Карточка администратора безопасно ограничена лимитом Telegram 4096 символов даже после HTML escaping.
13. Незавершённые анкеты закрываются по таймауту, а повторные отклонённые заявки ограничены cooldown без повторного AI-скоринга.

## Что взято из готовых проектов

Базовый Telegram-процесс не проектировался с нуля. За основу взят проверенный паттерн проекта
[Ringo](https://github.com/why-not-try-calmer/ringo): `ChatJoinRequest -> ЛС -> questionnaire -> admin verdict`.
Ringo распространяется по MIT; лицензия сохранена в `LICENSE.ringo`.

Идея LLM-assisted gatekeeping и принцип «не пускать пользователя в группу до завершения проверки»
сверялись с [Bouncer](https://github.com/k4yt3x/bouncer). Его код не копировался, так как проект AGPL-3.0.

См. `THIRD_PARTY_NOTICES.md`.

## Архитектура

```text
Telegram join request
        |
        v
ChatJoinRequestHandler
        |
        v
Private interview (3 answers)
        |
        v
Persistent DB state
        |
        v
LLM scorer
   |          |
   |          +--> ambiguous / acceptable --> Admin chat card
   |                                      [Approve] [Reject]
   |
   +--> obvious spam / clear mismatch --> automatic decline
```

## Почему AI не может автоматически одобрить

ТЗ требует автоматический отказ при явном спаме/несоответствии и карточку кандидата для админов.
Поэтому в этой версии AI используется как скоринг + фильтр очевидных отказов. Пограничные и нормальные
заявки остаются на финальном решении администратора. Это уменьшает риск ложного допуска и ложного отказа.

## Формула Confidence Score

```text
0.35 * location
+ 0.45 * business
+ 0.20 * intent
- 0.55 * spam
```

Результат ограничивается диапазоном 0..100. Сам `Confidence Score` не используется как единственная
причина автоотказа. Автоотказ определяется отдельными консервативными порогами.

## Требования Telegram

- Целевой чат должен принимать заявки на вступление.
- Бот должен быть администратором целевого чата.
- Боту нужно право управлять заявками / приглашать пользователей (`can_invite_users`).
- Создайте отдельный закрытый чат администраторов и добавьте туда бота.
- `TARGET_CHAT_ID` и `ADMIN_CHAT_ID` — числовые ID, обычно вида `-100...`.

`ChatJoinRequest.user_chat_id` используется сразу после заявки для открытия ЛС с кандидатом.

## Запуск через Docker

```bash
cp .env.example .env
# заполните .env

docker compose up -d --build
```

Логи:

```bash
docker compose logs -f gatekeeper
```

Остановка:

```bash
docker compose down
```

## Запуск без Docker

```bash
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\\Scripts\\activate
pip install -r requirements.txt
cp .env.example .env
```

Экспортируйте значения из `.env` в окружение и запустите:

```bash
python -m app.main
```

Сам проект намеренно не читает `.env` самостоятельно: в Docker это делает `env_file`, а в production
секреты лучше передавать средствами окружения/secret manager.

## LLM

Используется OpenAI-compatible endpoint:

```text
POST {LLM_BASE_URL}/chat/completions
```

Нужно указать:

```env
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=...
LLM_MODEL=...
```

Если используемый провайдер не поддерживает `response_format: {type: json_object}`, бот автоматически
повторит запрос без этого параметра и всё равно провалидирует JSON-ответ.

Важно: ответы анкеты отправляются выбранному LLM-провайдеру. Это необходимо учитывать в политике
конфиденциальности сообщества.

## Порог автоматического отказа

По умолчанию:

```env
AUTO_REJECT_SPAM_SCORE=85
AUTO_REJECT_CORE_SCORE_MAX=15
AUTO_REJECT_MIN_AI_CONFIDENCE=80
INTERVIEW_TIMEOUT_MINUTES=30
REAPPLICATION_COOLDOWN_MINUTES=60
MAINTENANCE_INTERVAL_SECONDS=60
```

Автоматический отказ происходит только если `ai_confidence >= 80` и выполняется хотя бы одно условие:

- `spam_score >= 85`;
- `location_score <= 15`;
- `business_score <= 15`.

Если AI не уверен, даже очень плохой score не приводит к автоматическому отказу — карточка уходит админам.

## Карточка администратора

Карточка показывает:

- имя / username / Telegram ID;
- три исходных ответа;
- итоговый Confidence Score;
- оценки по четырем компонентам;
- уверенность AI;
- краткое саммари;
- флаги риска;
- кнопки `✅ Одобрить` и `❌ Отклонить`.

После успешного решения кнопки удаляются, повторное решение по той же заявке блокируется на уровне состояния БД. Если Telegram API не подтверждает действие (например, пользователь уже отозвал заявку), состояние БД не меняется и карточка остаётся доступной администратору.

## Команда `/status`

В админ-чате доступна команда:

```text
/status
```

Она показывает количество заявок по статусам.

Если `ADMIN_USER_IDS` не задан, кнопку решения и `/status` могут использовать только owner/admin
закрытого админ-чата. Если список задан, разрешены только явно перечисленные Telegram user ID.

## База данных

По умолчанию используется SQLite:

```env
DATABASE_URL=sqlite+aiosqlite:///./data/gatekeeper.db
```

Для нескольких реплик приложения используйте PostgreSQL, например:

```env
DATABASE_URL=postgresql+asyncpg://gatekeeper:password@db:5432/gatekeeper
```

Для первого production-релиза достаточно одной реплики + SQLite volume. Для HA/масштабирования — PostgreSQL.

## Тесты

```bash
pytest -q
```

Тестируются формула Confidence Score, консервативные правила автоотказа, JSON-парсер LLM, лимит Telegram-карточки, использование private chat ID, отсутствие ложного отказа при ошибке Telegram API и обработка ошибки стартового ЛС.
