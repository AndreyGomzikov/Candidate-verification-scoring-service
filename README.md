# Микросервис  «Верификация и скоринг кандидатов»

Telegram-микросервис для автоматической верификации и скоринга кандидатов перед вступлением
в закрытый чат Solidus.

## Что реализовано по ТЗ

1. Перехват `ChatJoinRequest` целевого Telegram-чата.
2. Немедленный старт диалога с кандидатом в ЛС.
3. Последовательная анкета из трех обязательных блоков:
   - локация / территория Грузии / даты приезда;
   - бизнес-профиль, роль, ниша, ссылки;
   - цель вступления и потенциальная польза сообществу.
4. AI-скоринг:
   - `location_score`;
   - `business_score`;
   - `intent_score`;
   - `spam_score`;
   - `ai_confidence`;
   - итоговый `Confidence Score`;
   - краткое русскоязычное саммари и флаги риска.
5. Автоотказ только при очевидном спаме или очевидном несоответствии одному из ключевых критериев
   и только при высокой уверенности AI.
6. Все остальные кандидаты уходят в закрытый админ-чат карточкой с кнопками
   `Одобрить` / `Отклонить`.
7. Решение администратора вызывает Telegram API `approveChatJoinRequest` / `declineChatJoinRequest`.
8. Состояние анкеты и результаты скоринга сохраняются в БД.
9. При сбое AI кандидат не отклоняется автоматически: заявка уходит администратору с пометкой об ошибке.
10. При ошибке Telegram API статус в БД меняется только после подтверждённого `approve/decline`; технический сбой не превращается в ложный отказ.
11. Для последующих уведомлений сохраняется реальный private chat ID из диалога с кандидатом; код не предполагает, что `user_id == chat_id`.
12. Карточка администратора безопасно ограничена лимитом Telegram 4096 символов даже после HTML escaping.
13. Незавершённые анкеты закрываются по таймауту, а повторные отклонённые заявки ограничены cooldown без повторного AI-скоринга.

## Что взято из готовых проектов

Базовый Telegram-процесс не проектировался с нуля. За основу взят проверенный паттерн проекта
[Ringo](https://github.com/why-not-try-calmer/ringo): `ChatJoinRequest -> ЛС -> questionnaire -> admin verdict`.
Ringo распространяется по MIT; лицензия сохранена в `LICENSE.ringo`.

Идея LLM-assisted gatekeeping и принцип «не пускать пользователя в группу до завершения проверки»
сверялись с проектом [Bouncer](https://github.com/k4yt3x/bouncer).

## Архитектура

```text
Telegram join request
        |
        v
ChatJoinRequestHandler
        |
        v
Private interview (3 answers)
        |
        v
Persistent DB state
        |
        v
Stage 1: LLM scorer (оценки и типизированное предложение, НЕ решение)
   |          |
   |          +--> нет явного основания --> Admin chat card
   |                                             [Approve] [Reject]
   |
   +--> возможный отказ: criterion, evidence_quote, spam_type
                  |
                  v
      Stage 2: Independent LLM review (все 3 ответа, строгий JSON)
                  |
                  v
      Stage 3: Deterministic Decision Gate (app/decision.py)
         |                                  |
         |                                  +--> ошибка / противоречие /
         |                                        нет доказательств --> Admin
         |
         +--> ВСЕ проверки пройдены --> Telegram automatic decline
```

## Почему AI не может автоматически одобрить

ТЗ требует автоматический отказ при явном спаме/несоответствии и карточку кандидата для админов.
Поэтому в этой версии AI используется как скоринг + фильтр очевидных отказов. Пограничные и нормальные
заявки остаются на финальном решении администратора. Это уменьшает риск ложного допуска и ложного отказа.

## Формула Confidence Score

```text
0.35 * location
+ 0.45 * business
+ 0.20 * intent
- 0.55 * spam
```

Результат ограничивается диапазоном 0..100. Сам `Confidence Score` не используется как единственная
причина автоотказа. Автоотказ определяется отдельными консервативными порогами.

## Требования Telegram

- Целевой чат должен принимать заявки на вступление.
- Бот должен быть администратором целевого чата.
- Боту нужно право управлять заявками / приглашать пользователей (`can_invite_users`).
- Создайте отдельный закрытый чат администраторов и добавьте туда бота.
- `TARGET_CHAT_ID` и `ADMIN_CHAT_ID` — числовые ID, обычно вида `-100...`.

`ChatJoinRequest.user_chat_id` используется сразу после заявки для открытия ЛС с кандидатом.

## LLM

Используется OpenAI-compatible endpoint:

```text
POST {LLM_BASE_URL}/chat/completions
```

Нужно указать:

```env
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=...
LLM_MODEL=...
```

Если используемый провайдер не поддерживает `response_format: {type: json_object}`, бот автоматически
повторит запрос без этого параметра и всё равно провалидирует JSON-ответ.

Важно: ответы анкеты отправляются выбранному LLM-провайдеру. Это необходимо учитывать в политике
конфиденциальности сообщества. **Если первичный скоринг предлагает автоотказ, выполняется
дополнительный запрос к тому же LLM-провайдеру** для независимой смысловой проверки всей анкеты;
это увеличивает стоимость/время обработки только таких заявок. Ошибка, невалидный JSON,
неоднозначность или отсутствие ответа на втором этапе приводят к **ручной проверке**, а не
к отказу. Отдельный API-ключ, миграция БД и новые настройки не требуются.

## Порог автоматического отказа

По умолчанию:

```env
AUTO_REJECT_SPAM_SCORE=85
AUTO_REJECT_CORE_SCORE_MAX=15
AUTO_REJECT_MIN_AI_CONFIDENCE=80
INTERVIEW_TIMEOUT_MINUTES=30
REAPPLICATION_COOLDOWN_MINUTES=60
MAINTENANCE_INTERVAL_SECONDS=60
```

**Нормализация `ai_confidence`.** Первый AI должен возвращать уверенность
**целым числом от 0 до 100**, например `70` или `85`. Для совместимости с
LLM, возвращающими вероятность от 0 до 1, парсер переводит дробные значения
строго между `0` и `1`: `0.7` → `70`, `0.85` → `85`, `0.799` → `79`.
Используется округление **вниз**, чтобы результат `79.9%` не преодолел
порог `80` автоматически. Целые проценты `0`–`100` сохраняются, в том числе
`1` → `1` (не `100`). Некорректные значения, дробные проценты больше единицы,
булевы значения, бесконечности и неоднозначные форматы приводят к ручной
проверке через стандартную обработку ошибки первичного скоринга. Формула
`Confidence Score` и пороги автоматического отказа не меняются.

**Важно для уже существующих заявок:** обновление исправляет только новые
ответы AI. Записи, ранее сохранённые с `ai_confidence=0` при исходном `0.7`,
автоматически не пересчитываются: для повторной оценки нужна новая тестовая
заявка. Никаких миграций базы данных не требуется.

Первый этап **лишь предлагает** автоматический отказ, если `ai_confidence >= 80` и
выполнено одно из консервативных условий:

- `spam_score >= 85`, `spam_type` принадлежит `advertising`, `fraud`, `mass_template` или
  `manipulation`, а дословная непрерывная цитата `spam_evidence` из ответа содержит конкретный
  признак соответствующего нарушения. Дополнительно анализируется **полный контекст всех ответов**:
  отрицания, предупреждения о мошенниках, пересказ или критика рекламы не дают автоотказа.
  Тип `gibberish` всегда передаётся администратору; без подтверждённой цитаты автоотказ невозможен;
- `location_score <= 15`, а `location_mismatch_evidence` — дословная цитата из ответа о локации,
  подтверждающая и нахождение вне Грузии, и отсутствие планов приезда. Планы переезда, например
  «через три месяца переезжаю в Тбилиси», купленные билеты или противоречивые
  сведения **в любом из трёх ответов** исключают автоотказ;
- `business_score <= 15`, а `business_mismatch_evidence` — дословная цитата из ответа о бизнесе,
  подтверждающая отсутствие бизнеса, проектов и деловой занятости. Инвестиции, финансирование
  стартапов, консультирование, фриланс и иная профессиональная роль, упомянутая
  **в любом из трёх ответов**, исключают автоотказ.

**Этап 1 — AI Scoring (`app/scoring.py`)**. AI даёт оценки, а код формирует
`RejectionProposal` со строго определёнными полями `criterion` (`location`,
`business`, `spam`), `evidence_quote`, `spam_type` и `reason`. Если явное основание
не найдено, заявка немедленно передаётся администратору. Текст причины отказа
нельзя использовать для определения категории в рабочем маршруте.

**Этап 2 — Semantic Verification (`AIScorer.review_rejection`)**. Отдельный
LLM-запрос независимо читает **все три полных ответа** и возвращает структурированный
`SemanticReview` со строгой схемой **v3**: `schema_version=3`, `verdict`, `criterion`, `spam_type`,
`field_checks`, `no_relevance_basis`, `field_evidence` (для каждого поля `supporting_quotes`,
`contradicting_quotes`, `uncertainty_reason`), `overall_consistency`,
`eligibility_signal`, `explanation_code`, `evidence_quote`.
Модель обязана рассмотреть **каждый** ответ: если возможны поездка, работа,
инвестиции либо контекст цитирования рекламы — это `contradicts` или `uncertain`,
а не `no_relevant_information`. Схемы v1/v2 не принимаются; при устаревшем JSON,
неполных данных или ошибке API кандидат переходит на ручную проверку.

**Этап 3 — Deterministic Decision Gate (`app/decision.py`)**. Это единственная
точка в рабочем маршруте, разрешающая автоматическое отклонение. Она **не делает
третьего AI-запроса** и независимо от AI проверяет:

1. Все **три ответа непустые**, присутствуют предложение и полноценный результат второго этапа.
2. Первичное предложение повторно воспроизводится на исходных баллах, порогах и
   текстах. Любое несоответствие или подмена причины блокирует автоотказ.
3. Совпадают **точные категории** обоих этапов; для спама совпадает `spam_type`.
4. Второй AI явно выставил `verdict=reject`; `overall_consistency=consistent`,
   `eligibility_signal=absent`; во всех трёх ответах нет `contradicts`/`uncertain`.
   Код `explanation_code` должен соответствовать категории отказа.
5. **Все цитаты `field_evidence` проверяются по своему полю** (а не по всей
   анкете). Для `supports_rejection` обязательно конкретное доказательство;
   для `no_relevant_information` исходный ответ должен быть явно нейтральной
   короткой фразой из строгого списка; одной отметки AI недостаточно.
   Главная `evidence_quote` должна дословно совпадать с одной из подтверждающих
   цитат. **Для отказа по локации/бизнесу в двух остальных полях разрешён только
   `no_relevant_information` с подтверждённой нейтральной фразой.** Если AI
   ошибочно называет содержательное уточнение `supports_rejection`, даже с
   подлинной цитатой, Decision Gate блокирует отказ: смысл цитаты не доказан.
   **В самом профильном поле** действует дополнительная обязательная проверка:
   цитата должна охватывать ВЕСЬ ответ, а весь ответ — точно соответствовать
   одной из коротких однозначных отрицательных формулировок, распознаваемых
   строгой грамматикой в `app/scoring.py`. Наличие другого предложения,
   уточнения, неизвестной формулировки или несоответствие цитаты полному ответу
   блокирует автоотказ независимо от совпадающих выводов обоих AI.
   Проверяется также **исходная пунктуация**, а не только слова: вопросы
   (`?`, `？`, `⁇` и другие знаки вопроса), цитирование, многоточия,
   несколько предложений и необычные разделители требуют ручной проверки.
   В однозначном коротком ответе допускаются запятые между словами и одна
   завершающая точка. Две AI-проверки не могут обойти это правило.
   Это преднамеренно увеличивает долю ручной проверки: даже явно отрицательный,
   но нестандартный свободный ответ не отклоняется автоматически.
   Для спама действует отдельная проверка подтверждающего контекста.
   Противоречащие цитаты, непроверяемые фрагменты и выявленные в
   нераспознанные содержательные ответы блокируют отказ.
6. Только после разрешения Gate выполняется `decline_chat_join_request`;
   запись `auto_rejected` в БД возможна после успеха Telegram API.

При любой ошибке, недостающих полях, противоречиях или недостаточном доказательстве
заявка передаётся **единственному администратору** для решения. Третий этап
не проверяет истинность утверждений кандидата и не даёт математической гарантии
от одинаковых смысловых ошибок двух AI-проверок, хотя теперь не доверяет
их утверждениям об отсутствии релевантных фактов в свободном тексте. В нём остаются консервативные регулярные
проверки контекста, которые могут увеличить число ручных разборов.

Новые настройки, миграция БД и дополнительные AI-запросы (по сравнению с
двухэтапной версией) не требуются. Ошибки третьего этапа протоколируются
кодом причины, без записи текста анкеты в журнал.

При сомнениях, отрицаниях или смешанных формулировках заявка уходит администратору:
строгие автоматические правила намеренно предпочитают ручную проверку ложному отказу.

Если AI не уверен, даже очень плохой score не приводит к автоматическому отказу — карточка уходит админам.

Принцип: автоотказ — только при явных фактах. Пустые, шуточные, тестовые («тестирую бота») или
уклончивые ответы — это `spam_type = low_effort` и низкий `intent_score`; такие заявки уходят
администратору, а не отклоняются автоматически. Высокий `spam_score` без конкретного типа спама
(или если поле `spam_type` отсутствует в ответе модели) тоже не приводит к автоотказу.
Причина отказа в карточке называет конкретный тип спама и цитату-доказательство.

Confidence Score — только ориентир для админа, на решение он не влияет. Если AI сам указал
`spam_type` = `none` или `low_effort`, в формуле используется спам-риск не выше 40, чтобы
противоречивая оценка модели не занижала Score кандидату без признаков спама.

## Карточка администратора

Карточка показывает:

- имя / username / Telegram ID;
- три исходных ответа;
- итоговый Confidence Score;
- оценки по четырем компонентам;
- уверенность AI;
- краткое саммари;
- флаги риска;
- кнопки `✅ Одобрить` и `❌ Отклонить`.

После успешного решения кнопки удаляются, повторное решение по той же заявке блокируется на уровне состояния БД. Если Telegram API не подтверждает действие (например, пользователь уже отозвал заявку), состояние БД не меняется и карточка остаётся доступной администратору.

## Команда `/status`

В админ-чате доступна команда:

```text
/status
```

Она показывает количество заявок по статусам.

Если `ADMIN_USER_IDS` не задан, кнопку решения и `/status` могут использовать только owner/admin
закрытого админ-чата. Если список задан, разрешены только явно перечисленные Telegram user ID.

## База данных

По умолчанию используется SQLite:

```env
DATABASE_URL=sqlite+aiosqlite:///./data/gatekeeper.db
```

Для нескольких реплик приложения используйте PostgreSQL, например:

```env
DATABASE_URL=postgresql+asyncpg://gatekeeper:password@db:5432/gatekeeper
```

Для первого production-релиза достаточно одной реплики + SQLite volume. Для HA/масштабирования — PostgreSQL.

## Тесты

```bash
pytest -q
```

Тестируются формула Confidence Score, консервативные правила предварительного отбора,
второй смысловой AI-проход (его JSON-схема и проверка всех трёх ответов),
отдельный строгий третий этап (`tests/test_decision.py`), включая подмену категории,
отсутствующие доказательства, противоречия, неверный тип спама и сбои,
маршрутизация в Telegram,
лимит Telegram-карточки и технические сбои. В тестах ответ LLM моделируется:
это не замена интеграционному испытанию с реальным провайдером.


## Двусторонняя связь с кандидатами (обращения)

После **третьего ответа** анкеты (включая AI-проверку, ожидание администратора,
одобрение, ручной/автоматический отказ и истечение срока анкеты) последующие
**текстовые** сообщения в личном чате бота становятся обращениями. Ответы во
время первых трёх вопросов остаются частью анкеты и не пересылаются.

1. Кандидат пишет боту. Бот создаёт/находит открытое обращение `#ID` и публикует
   сообщение в существующей группе `ADMIN_CHAT_ID`. Кандидату отправляется
   подтверждение, **только если Telegram подтвердил пересылку**.
2. Администратор отвечает с помощью функции Telegram **«Ответить» именно на
   карточку обращения, отправленную ботом**. Сообщение доставляется кандидату
   от имени бота в формате «💬 Ответ администрации Solidus:» без имени
   конкретного администратора. ID ответившего сохраняется только для
   внутреннего учёта. Ответы на чужие сообщения или обычный текст в группе не
   пересылаются. Бот должен состоять в группе модерации; при включённом
   Telegram Privacy Mode он видит ответы на собственные сообщения.
3. У карточки есть кнопка **«✅ Закрыть обращение»**. Закрыть его может только
   администратор, которому разрешена модерация. Следующее сообщение кандидата
   создаст новое обращение. Открытое обращение остаётся тем же при новых
   сообщениях, в том числе после перезапуска контейнера.
4. Сообщения, состояния доставки и Telegram message ID сохраняются в
   PostgreSQL в таблицах `support_tickets` / `support_messages`.
   При сбое Telegram сообщение остаётся в очереди; фоновый цикл повторяет
   доставку до 8 попыток с увеличивающейся задержкой (до 1 часа между
   попытками). После исчерпания попыток запись помечается `failed` и
   сохраняется для диагностики. Повторно отправлять её вручную кандидату
   **не нужно**. В логи не записываются тексты сообщений или токены.
   Бот использует `MAINTENANCE_INTERVAL_SECONDS` (обычно 60 секунд) для
   опроса очереди.
5. Ограничение частоты сообщений защищает модераторов от спама. Команды
   `/start` и `/status` не превращаются в обращения. Текст ограничен
   `MAX_ANSWER_LENGTH` (по умолчанию 2500 символов).
6. Статус заявки, AI-скоринг и вступление в группу от переписки **не меняются**.
   Диалог с новым пользователем, не подававшим заявку, автоматически не
   транслируется администраторам.


**Обновление на существующем PostgreSQL:** при запуске `Database.init()`
сначала создаёт отсутствующие таблицы, а затем выполняет совместимую миграцию:
добавляет в `support_messages` поля `delivery_status`, `delivery_attempts`,
`next_attempt_at`, переводит уже доставленные сообщения в статус `delivered`
и создаёт **частичный уникальный индекс** на одного открытого тикета в расчёте
на одного пользователя. Если в старой БД уже образовались несколько открытых
обращений одного пользователя, остаётся открытым самое новое; остальные
помечаются закрытыми, без удаления истории. Миграция идемпотентна, но перед
деплоем **обязательно сделайте резервную копию PostgreSQL** и убедитесь, что
приложение запускается с нужными правами на изменение схемы.
Существующие заявки в `candidates` не меняются. **Не запускайте**
`docker compose down -v` и не удаляйте том БД.

**Семантика доставки:** Telegram Bot API не поддерживает ключ идемпотентности
для `sendMessage`. При аварии *после* успешной отправки, но *до* фиксации
результата в БД, повторная попытка может создать вторую карточку/сообщение.
У карточки теперь есть служебная строка `🆔 Сообщение #N`. Если администратор
ответит на первоначальную карточку, бот безопасно восстановит привязку к
исходному обращению, даже когда Telegram ID карточки не успел сохраниться.
Фоновый цикл возвращает «зависшие» операции в работу через 5 минут. В обоих
случаях у ответа кандидату одинаковый анонимный отправитель — сам бот.
Точная гарантия «один раз и только один раз» для Telegram недостижима; очередь
обеспечивает доставку с возможными редкими дублями после аварий.

Тест: одобрите/отклоните заявку → напишите боту → найдите карточку с номером
обращения в чате модерации → ответьте на карточку через «Ответить» → проверьте
личный чат кандидата → закройте обращение → напишите ещё раз и убедитесь, что
создан новый номер. После перезапуска бота откройте старое обращение: связь с
предыдущей карточкой должна сохраниться.


### Обработка окончательно недоставленных сообщений (надёжность поддержки)

- Сообщения кандидатов модераторам, ответы модераторов и уведомления о закрытии
  обращения хранятся в **одной очереди `support_messages`**. Уведомление
  `ticket_closed` создаётся **в той же транзакции**, в которой обращение меняет
  статус на `closed`; повторное закрытие не создаёт второе уведомление.
- Если Telegram временно недоступен, бот повторяет отправку с увеличивающейся
  задержкой. Сообщение, для которого исчерпано **8 попыток**, получает статус
  `failed`. В той же транзакции создаётся служебное оповещение `delivery_alert`
  для группы модерации с кнопкой **«🔄 Повторить доставку»**. Оповещение также
  хранится в очереди и может повторяться после сбоя Telegram. Оно не
  превращается в сообщение кандидату при ответе на него через «Ответить».
- Повторная отправка выполняется по кнопке только уполномоченным модератором;
  второе нажатие не создаёт дубликат. Если даже оповещение недоставлено,
  в группе модерации доступны команды `/support_failed` (последние 15 неуспешных
  доставок) и `/support_retry 123` (номер **исходного** сообщения из списка).
  Повторно отправлять чужие сообщения неуполномоченные участники не могут.
- Уведомление о закрытии ждёт завершения более ранних ответов администратора
  по этому обращению: сначала ответ, затем уведомление о закрытии. Если прежний
  ответ окончательно не доставлен, закрытие не блокируется навсегда.
- Дубли оповещений об одной ошибке подавляются уникальным индексом
  `uq_support_delivery_alert_per_message`. Когда оригинальное сообщение
  повторно принято к отправке, ненужное *ещё не отправленное* оповещение
  отменяется. Если сбой повторится, оно снова активируется.
- При запуске обновления в существующей базе автоматически добавляется
  `support_messages.related_message_id` (nullable FK на сообщение) и индекс.
  Исторические обращения не удаляются; сделайте резервную копию PostgreSQL
  перед деплоем. Не удаляйте volume. Миграция выполняется повторно безопасно.
- Даже с очередью Telegram Bot API не гарантирует exactly-once при падении
  процесса между отправкой и фиксацией её результата. В редких случаях возможен
  дубль; администраторская карточка сохраняет служебный маркер для восстановления.
  Когда оповещение об ошибке тоже невозможно отправить, используйте
  `/support_failed` после восстановления доступа к Telegram или логи сервера.


## Финальный Decision Gate: контракт v3

Второй AI должен вернуть строго `schema_version=3`, три `field_checks`, три
`field_evidence`, `no_relevance_basis` для каждого поля, `overall_consistency`,
`eligibility_signal`, `explanation_code` и цитату `evidence_quote`. **Свободное
поле `explanation` запрещено**: решение и текст причины отказа формирует Python
после независимой проверки подтверждающей цитаты. Устаревшие ответы v2,
неизвестные поля и некорректные JSON передаются администратору.

Статус `no_relevant_information` допускается лишь при
`no_relevance_basis=explicit_neutral`, когда **сам исходный ответ** строго
соответствует небольшому списку нейтральных формулировок в `app/decision.py`.
Для отказа по локации/бизнесу отрицательная цитата из профильного ответа
тоже недостаточна: она должна совпадать со ВСЕМ ответом, а тот — с
ограниченной грамматикой явных отрицательных утверждений. Уточнения внутри
профильного поля блокируют автоотказ. Этот механизм не пытается доказывать
смысл произвольного текста с помощью ключевых слов.

Для любого другого содержательного ответа, даже если оба AI посчитали его
нерелевантным, автоотказ запрещён. Это преднамеренный компромисс: число
ручных проверок увеличится, зато совпадающие ошибки моделей не приведут к
автоматическому отклонению известных и непредусмотренных формулировок.

Для тестирования использовать:

```bash
python -m pytest -q
```
