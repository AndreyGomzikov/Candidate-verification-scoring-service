# Исправление обработки отсутствующих Telegram-заявок

**Проблема:** при истечении незаполненной анкеты Telegram возвращал
`BadRequest: Hide_requester_missing`, поскольку заявка была отозвана или уже
обработана. Gatekeeper переводил анкету в `pending_admin` и публиковал карточку
с кнопками, которые не могли выполнить действие.

**Изменения:**

- При `Hide_requester_missing` в обработчике истечения времени анкета получает
  `expired` с явной причиной **без записи об успешном отклонении в Telegram**.
  Карточка для модерации не создаётся. Сетевые ошибки, нехватка прав и другие
  ошибки Telegram по-прежнему ведут в `pending_admin` (fail closed).
- Если администратор нажал старую кнопку и Telegram вернул
  `Hide_requester_missing`, запись становится `request_missing` и кнопки
  удаляются, если Telegram разрешил редактирование карточки. Ни `approved`, ни
  `rejected` не записываются: фактический результат заявки неизвестен.
- Новая Telegram-заявка с более поздней датой может заменить старую активную
  анкету в `interview` / `pending_admin`. Повторная доставка того же события
  сохраняет старую анкету, а выполняющийся `scoring` не прерывается. Точность
  даты Telegram составляет одну секунду, поэтому используется защитный
  допуск; очень быстрые повторные заявки могут потребовать ручной проверки.
- `expired` с причиной `Hide_requester_missing` не приводит к блокировке
  следующей заявки по `REAPPLICATION_COOLDOWN_MINUTES`. Обычные `expired`,
  `rejected` и `auto_rejected` сохраняют прежний cooldown.
- Существующие записи в PostgreSQL не меняются автоматически. Уже вручную
  закрытая заявка №31 остаётся в статусе `expired`. Карточка в Telegram не
  удаляется задним числом.

**Развёртывание:** запустить `python -m pytest -q` в CI; создать резервную
копию PostgreSQL; выполнить обычное развертывание через workflow для `main`.
Новых переменных `.env` и миграций схемы БД не требуется (`status` — VARCHAR).
Проверять на тестовом канале, прежде чем включать в production.

## Дополнительная защита перед развёртыванием (06.11.2026)

**Устранена гонка между обработчиками одного кандидата:**

- Для пары `(target_chat_id, user_id)` `on_join_request`, обработка ответов,
  таймаут и решение модератора используют общую асинхронную блокировку.
  Финальная операция AI-скоринга также получает эту блокировку, но во время
  сетевых LLM-запросов блокировка **не удерживается**.
- При PostgreSQL дополнительно берётся `pg_advisory_xact_lock`, который
  сериализует эти операции **между несколькими процессами бота**, автоматически
  освобождается при завершении транзакции или разрыве соединения. В тестовом
  SQLite блокировка действует в рамках экземпляра обработчика.
- Перед закрытием просроченной анкеты бот повторно читает состояние в БД,
  проверяет активную запись и время последнего изменения. При расхождении
  обработка пропускается. После Telegram-вызова используется атомарное
  сравнение-и-обновление (`transition_status_if`) по статусу, этапу и времени.
  `superseded` не перезаписывается на `expired`.
- Подтверждённо новое событие `ChatJoinRequest` заменяет старую анкету даже
  тогда, когда старый скоринг ещё выполняется. Результат устаревшего скоринга
  не используется для отклонения новой заявки.
- Действия модератора повторно проверяют состояние под блокировкой, а
  переходы в `approved`, `rejected`, `request_missing` выполняются через CAS.
- В финальном этапе AI-скоринга применяется дополнительная проверка статуса
  и CAS для конечных статусов. Сбой обновления не подтверждает решение.
- Удалены побочные изменения переносов строк из 12 файлов: они полностью
  совпадают с исходной версией и не входят в итоговый патч.

**Принципиальное ограничение Telegram Bot API.** Методы
`approve_chat_join_request` и `decline_chat_join_request` принимают только
ID группы и ID пользователя, **не ID отдельной попытки вступления**. Если
пользователь самостоятельно отзывает заявку и снова подаёт её между моментом
проверки ботом и вызовом API, Telegram может применить действие к новой
заявке ещё до того, как новый `ChatJoinRequest` получен ботом. Ни SQL-CAS,
ни блокировка в приложении не могут исключить такой внешний сценарий на 100%.
Для строгого запрета такого риска необходим другой продуктовый процесс —
например, отказаться от автоматического отклонения по истечении таймаута и
передать очистку заявок администратору непосредственно в Telegram.

### Проверки и выпуск

1. Запустить в CI `python -m compileall -q app tests`, `python -m pytest -q`,
   `git diff --check` и сборку Docker-образа.
2. Проверить, что интеграционные SQLite-тесты не пропущены: CI устанавливает
   `aiosqlite` из `requirements.txt`.
3. До обновления VPS сделать резервную копию PostgreSQL и сохранить SHA
   предыдущего работающего релиза.
4. Проверить на отдельном тестовом Telegram-сообществе: обычную заявку,
   повторную подачу во время AI-скоринга, истечение времени после отзыва,
   действие со старой карточки, сетевой сбой и доставку сообщения кандидату.
5. Только после успешного CI и ручной проверки тестового сообщества сливать PR
   в `main`: текущий workflow автоматически выполняет production deploy.

Новых переменных окружения или миграций не требуется. PostgreSQL advisory
locks работают с существующей БД. Изменения не исправляют задним числом старые
карточки модерации.

## Дополнение: исправления №3 и №4

- Новое поле `candidates.request_date` сохраняет `ChatJoinRequest.date`. При
  перезапуске бота отложенная повторная доставка события с прежним timestamp
  **не создаст новую анкету**, даже если событие пришло гораздо позже.
- Сравнение с `created_at` и искусственный допуск в секунду удалены. Только
  строго более поздний timestamp Telegram заменяет активную запись.
- При повторной подаче в ту же секунду (и для исторических записей с NULL
  `request_date`) API не даёт надёжного идентификатора попытки: сохраняется
  действующая анкета, требуется проверка оператором, если повторная подача
  не распознаётся. Это сознательный fail-safe режим.
- `Database.init()` добавляет nullable-колонку в существующий PostgreSQL или
  SQLite. ПЕРЕД развёртыванием сделать резервную копию БД; для PostgreSQL
  отдельно допустимо выполнить `ALTER TABLE candidates ADD COLUMN IF NOT
  EXISTS request_date TIMESTAMP WITH TIME ZONE;`.
- Добавлен отдельный тест `tests/test_postgres_join_lock.py`: два независимых
  `Database`/подключения пытаются получить advisory lock на одного кандидата.
  Запускать только на **изолированной** тестовой БД, например:
  `GATEKEEPER_TEST_POSTGRES_URL=postgresql+asyncpg://... python -m pytest -q tests/test_postgres_join_lock.py`.
  Без переменной тест помечается SKIP и **не считается выполненной проверкой
  PostgreSQL**. Этот тест не обращается к Telegram и не изменяет записи.
- Telegram не позволяет указать конкретную попытку в approve/decline;
  блокировки между ботами не устраняют гонку с отзывом заявки пользователем.

## Дополнение: защита от повтора cooldown-отказов (06.11.2026)

- Новая таблица `cooldown_declined_join_requests` сохраняет пару
  `(target_chat_id, user_id)` и `ChatJoinRequest.date` **после успешного**
  `decline_chat_join_request` во время cooldown. Это отдельный журнал, а не
  анкета кандидата: показатели анкет и срок cooldown не изменяются.
- При очередном `ChatJoinRequest` обработчик сравнивает время события с
  журналом отказов и последней анкетой. Дубликаты, пришедшие **после окончания
  cooldown**, больше не создают новую анкету. Более поздняя заявка может
  пройти обычный сценарий.
- `Base.metadata.create_all()` создаёт эту дополнительную таблицу при
  стандартном `Database.init()`; исторические таблицы не удаляются. Для
  production требуется предварительный бэкап и разрешение на DDL.
- Проверки: `tests/test_request_lifecycle.py` (включая отказ Telegram и сбой
  доставки ЛС), `tests/test_request_lifecycle_db.py` (уникальность, область
  чата, сохранение между перезапусками).

**Ограничения:** исторические cooldown-отказы, обработанные до обновления,
не имеют записи в журнале. Telegram не даёт уникальный ID попытки и
транзакцию вместе с БД, поэтому невозможно полностью исключить внешнюю гонку
«пользователь отозвал и снова подал заявку во время вызова API». Теперь
отказ во время cooldown сначала записывается как `pending` до API;
при сбое результат остаётся `pending` или становится `uncertain`, и
повторное событие не начинает новую анкету. Различить две заявки,
созданные в одну секунду, также нельзя. Нужно проверить новый сценарий в
тестовом Telegram-чате перед production.

## Дополнение: устойчивое отклонение во время cooldown (06.11.2026)

- Для **каждой новой Telegram-попытки** с известным `ChatJoinRequest.date` сначала
  коммитится намерение `cooldown_declined_join_requests.status='pending'`.
  После успешного `decline_chat_join_request()` запись становится `declined`
  (`confirmed_at`); после TelegramError — `uncertain`.
- Журнал является маркером обработки **для всех трёх состояний**. Если бот
  аварийно завершился после коммита намерения, та же старая попытка не будет
  принята как новая после окончания cooldown. Неопределённая операция
  **не считается подтверждённым отказом**.
- `Database.init()` добавляет три колонки к существующей таблице:
  `status VARCHAR(16) NOT NULL DEFAULT 'declined'`, `confirmed_at`, `alerted_at`.
  Исторические успешные отказы сохраняются и получают состояние `declined`.
  `declined_at` оставлено для совместимости: в новых строках это время
  регистрации намерения, а не доказательство успешного вызова Telegram.
- При старте и далее в цикле обслуживания намерения `pending` старше пяти минут
  переводятся в `uncertain`. Администратору отправляется предупреждение о
  необходимости проверить заявку вручную. При неуспехе доставки предупреждение
  повторяется; после успеха сохраняется `alerted_at`.
- **Автоматически повторять отказ запрещено:** Telegram API не предоставляет
  уникальный ID попытки. Повторный вызов `decline_chat_join_request` по `user_id`
  может отклонить уже другую новую заявку, поэтому статус `uncertain` должен
  проверять администратор непосредственно в Telegram.
- Событие без `request_date` во время cooldown не отклоняется автоматически;
  соответствующая аномалия попадает в лог. Старые отказы до введения журнала
  по-прежнему нельзя восстановить задним числом.
