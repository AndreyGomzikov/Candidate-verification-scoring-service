## Порядок безопасной проверки

1. Создать ветку от актуальной основы и перенести изменения; не пушить сразу в `main`.
2. Открыть pull request в `main`: job `Python tests and Docker build` поднимет временный PostgreSQL 16, поставит зависимости, выполнит тесты SQLite/PostgreSQL и проверит Docker-сборку.
3. Проверить, что все обязательные job успешны. Если CI сообщает `skipped`, выяснить причину: PostgreSQL-тесты в CI должны выполниться, а не пропускаться.
4. Выполнить smoke-проверку в **отдельном тестовом Telegram-чате/канале**, не в рабочем сообществе: новая заявка, прохождение анкеты, отказ из-за cooldown, повторная доставка того же update, действительная заявка после окончания cooldown. Для последнего используется отдельный регрессионный тест; Telegram не предоставляет API для искусственного повторного создания конкретного `ChatJoinRequest` на сервере.
5. Перед продакшеном сделать бэкап PostgreSQL: `Database.init()` добавляет колонку `candidates.request_date` и таблицу `cooldown_declined_join_requests`.
6. Только после успешных проверок выполнять merge в `main`: в текущем CI push в main **запускает автоматическое развёртывание на VPS**.

## Ограничения

- Старые события до внедрения журнала cooldown не имеют `request_date` в истории; гарантировать распознавание всех исторических дублей нельзя.
- События с одинаковой секундой Telegram не позволяют надёжно различить две попытки.
- В Git diff остались исходные изменения окончаний строк; по просьбе пользователя они не нормализованы. Если mandatory CI когда-либо вызывает `git diff --check`, потребуется отдельная очистка.


## Обновление: двухфазный cooldown и обязательные проверки CI

- Новый порядок: `begin_cooldown_decline()` → Telegram API →
  `complete_cooldown_decline(confirmed=True/False)`.
- Аварийно оставленные `pending` старше 5 минут маркируются `uncertain` и
  формируют предупреждение администратору. Повторять decline автоматически
  запрещено. Из-за ограничений Telegram состояние pending нельзя достоверно
  установить через Bot API; необходима ручная проверка.
- В тестах добавлены: отказ из-за сбоя БД **до Telegram**, сбой процесса **после
  фиксации намерения**, неоднозначный TelegramError, идемпотентный повтор,
  успешное/ошибочное извещение администратора, сохранение журнала после
  перезапуска и миграция исторического журнала.
- CI запускает все тесты с PostgreSQL 16 и проверяет JUnit XML: **любой
  пропущенный тест проваливает PR**. Разрушающая проверка старой схемы требует
  одноразовую БД `gatekeeper_ci` и явный флаг
  `GATEKEEPER_ALLOW_DESTRUCTIVE_SCHEMA_TEST=yes`, который выставлен только
  в тестовом CI.
- Необходи́мо проверить CI на GitHub и настоящий Telegram в тестовом сообществе:
  текущая локальная среда не содержит `aiosqlite`, `asyncpg` и сервера PostgreSQL.
- Важно: автоматическое слияние в `main` НЕ выполнять до зелёного CI, резервной
  копии БД и подтверждения, что пользовательские заявки в тестовом сообществе
  обрабатываются штатно.
- Окончания строк исходных файлов CRLF/LF намеренно сохранены.
